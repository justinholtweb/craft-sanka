# Sanka — plan

## What it is

Two jobs that share one machine.

**Instant indexing.** When a page changes, tell the engines *now* rather than waiting to be
crawled. Google's Indexing API, IndexNow (Bing, Yandex, Seznam, Naver, Yep — and through Bing,
ChatGPT Search and Copilot), and sitemap resubmission.

**GEO.** Generative engines do not crawl like search engines and are not managed like them. Sanka
manages the AI half explicitly: who may crawl, what they are given, who actually turned up, and
whether a page is written in a shape an answer engine can quote.

Reference point: the WordPress plugin *Instant Indexing for Google* (`fast-indexing-api`). Same
ground for the indexing half; the GEO half has no WordPress equivalent worth copying.

Named for instant coffee, which is the joke: indexing, but instant. And, being Sanka, it also
knows how to be *decaffeinated* — every engine can be put in dry-run and nothing leaves the server.

## The load-bearing idea: one ledger, many engines

Everything that could possibly want a URL indexed — an entry save, a status change, a delete, a
paste into the console, a bulk resubmit, a scheduled sweep, a console command, a retry — writes
**one row** into `sanka_submissions`:

    url · siteId · elementId · engine · type · reason · status · attempts · result

and one dispatcher drains it. Quota, deduplication, batching, backoff, reporting and the audit
trail are therefore written once and are identical no matter what caused the submission.

This is the whole architecture. Everything else hangs off it.

### Lifecycle of a row

    queued ──▶ pending ──▶ sent
                  │  ▲        (recorded with HTTP status and engine message)
                  │  └── retry, exponential backoff, capped
                  ├──▶ failed   (attempts exhausted, or a non-retryable answer)
                  └──▶ skipped  (cooldown, quota, dry run, rule said no)

`skipped` is a first-class outcome, not a silent drop. A URL that did not go anywhere always says
why it did not go anywhere — that is the difference between a tool you trust and a tool you poke.

## Engines

Each engine implements `EngineInterface` and answers the same six questions: am I configured, what
notification types do I take, how many URLs per call, what is my daily quota, what did the call
return, and what does that answer mean.

### Google Indexing API

- `POST https://indexing.googleapis.com/v3/urlNotifications:publish` — `{"url", "type"}`,
  type `URL_UPDATED` or `URL_DELETED`.
- `GET  https://indexing.googleapis.com/v3/urlNotifications/metadata?url=…` — last-seen status.
- `POST https://indexing.googleapis.com/batch` — `multipart/mixed`, up to 100 parts, 1 MB per part.
- Scope `https://www.googleapis.com/auth/indexing`, service account, RS256 JWT bearer grant.
- **Default quota is 200 publishes per project per day**, resetting at midnight Pacific. Sanka
  tracks it and stops rather than burning the last of it on a retry loop.
- The service account must be an **owner** of the Search Console property. Sanka cannot check that
  for you, but it can recognise the 403 that says so and print the fix instead of the status code.

Google documents the API as being for `JobPosting` and `BroadcastEvent` pages. Sanka says so on the
settings screen rather than pretending otherwise; in practice it is widely used more broadly, and
that is the operator's call to make knowingly.

### IndexNow

- Key: 8–128 characters from `[A-Za-z0-9-]`, generated by Sanka.
- Key file served at `https://host/<key>.txt` containing exactly the key. Sanka serves it from a
  route, so there is no file to forget to deploy.
- `POST /indexnow` with `{"host", "key", "keyLocation", "urlList"}`, up to 10,000 URLs.
- Submitting to one participating endpoint shares the submission with all of them, so Sanka uses
  `api.indexnow.org` by default and lets the operator pick a specific engine if they want to.
- Response codes carry real meaning and are mapped, not just logged: `200` accepted, `202` accepted
  pending key validation, `400` malformed, `403` key not found or wrong, `422` URL is not on this
  host, `429` slow down.

### Sitemaps

Google retired its sitemap ping endpoint in 2023 and the settings screen says so in those words.
What remains is real: resubmit to IndexNow (a sitemap URL is a URL), and re-warm Sanka's own view
of what a site contains. Pro only, because on its own it is not worth charging for.

## The GEO half (Pro)

### `llms.txt`

Generated from chosen sections into the emerging `llms.txt` shape — an H1 of site name, a blockquote
summary, then linked sections with one-line descriptions. `/llms.txt` is the map; `/llms-full.txt`
is the same map with the body text inlined. Both are served from routes and cached, and both are
opt-in per site.

### AI crawler policy

A table of the agents that matter — `GPTBot`, `OAI-SearchBot`, `ChatGPT-User`, `ClaudeBot`,
`Claude-User`, `Claude-SearchBot`, `PerplexityBot`, `Perplexity-User`, `Google-Extended`,
`Applebot-Extended`, `CCBot`, `Bytespider`, `Amazonbot`, `meta-externalagent`, `cohere-ai`,
`Diffbot`, `DuckAssistBot`, `YouBot`, `ImagesiftBot`, `Timpibot`, `Omgili` — each with what it is
actually for, because "block GPTBot" and "block OAI-SearchBot" have completely different
consequences and almost nobody knows which is which. Training crawlers, search crawlers and
user-initiated fetchers are labelled as such.

Output is `robots.txt` directives. Sanka will serve `/robots.txt` itself if asked, and refuses
quietly-wrong behaviour: if a static `robots.txt` exists in the web root it says so, because that
file wins and the setting would otherwise appear to do nothing.

### AI crawler visit log

The part with no equivalent anywhere. Every request whose user agent matches a known AI crawler is
recorded — agent, URL, status, timestamp — so the question "is ChatGPT actually reading this site,
and what is it reading" has an answer that is not a guess. Matching is a single precompiled regex
over the UA string and costs nothing on a miss. Rows age out on a retention setting.

### GEO readiness audit

Deterministic checks against a page's real HTML, scored and grouped:

- **Structure** — one H1, sane heading outline, answer-first opening, paragraph length, list and
  table density (quotable shapes), content-to-boilerplate ratio.
- **Attribution** — author, `datePublished`, `dateModified`, organisation.
- **Machine readability** — JSON-LD present and of a useful `@type`, FAQ/HowTo blocks, canonical,
  `hreflang`, no accidental `noindex`.
- **Citability** — numbers with sources, outbound references, definition-shaped sentences.

The HTML comes from one of two places: a same-origin fetch of the entry's own URL, or HTML pasted
into the CP. The fetch target is derived from Craft's site config, never from user input, so there
is no SSRF surface to fence off.

## Editions

**Lite** — Google Indexing API and IndexNow. Manual console, submit-on-save, the submissions
ledger, quota tracking, retries, one site's worth of rules.

**Pro** — everything above plus the GEO suite (`llms.txt`, crawler policy, visit log, readiness
audit), sitemap resubmission, scheduled sweeps, bulk resubmit by section, CSV export, and rules
across every site.

`Edition::…` is the single auditable statement of that boundary, taking `bool $isPro` so it can be
read and tested without an application. Rules that Lite cannot run are *refused on save* (so the
operator is told) and *downgraded on read* (so a lapsed licence degrades instead of breaking).

## Services

- `engines` — the registry, and `configured()`, which is the interesting half.
- `submissions` — the ledger. Queueing, deduplication, cooldown, status transitions, retention.
- `dispatcher` — drains the ledger. Batching, quota, backoff, result recording. The only place
  that calls an engine.
- `quota` — per engine per day, upserted, with Pacific-midnight reset for Google.
- `rules` — decides whether a given element change should become a submission, and for which
  engines. Section, entry type, site and status aware.
- `crawlers` — the AI agent registry, the policy, the `robots.txt` render, and the hit log.
- `llms` — `llms.txt` and `llms-full.txt` generation and caching.
- `geo` — the readiness audit.
- `urls` — the one place that decides whether a URL is submittable at all (absolute, public
  scheme, this site's host, not a `noindex` page, not a preview token).

## Hard rules

1. **Nothing leaves the server in dry run.** Dry run is per-engine, on by default on a fresh
   install, and the ledger records what *would* have been sent. An operator should be able to run
   Sanka for a week before letting it talk to anyone.
2. **Quota is checked before the call, not after the failure.** Burning quota to discover it is
   gone is the failure mode that makes these tools useless.
3. **A save storm must not cost quota.** Cooldown is keyed on url+engine+type and defaults to five
   minutes; twenty saves in a minute is one submission.
4. **Credentials are never written to the log, the ledger, or a template.** The service account is
   identified by fingerprint everywhere it is named.

## Testing

`tests/integration/checks.php`, run inside the plugin-testing container, self-cleaning, everything
it creates prefixed `sanka-check-`. Engines are exercised through a fake HTTP client, so the whole
submission path is covered without a single real outbound request.
